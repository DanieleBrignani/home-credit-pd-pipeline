## 2. Source grain, keys, cardinality, aggregation

| table | grain | primary key | join to parent | aggregation to applicant grain |
|---|---|---|---|---|
| `application_train` | one row per loan application (SK_ID_CURR) | `SK_ID_CURR` | - | none (already at applicant grain) |
| `application_test` | one row per unlabeled application (no TARGET) | `SK_ID_CURR` | - | NOT USED (no TARGET; ingested only for lineage completeness) |
| `bureau` | one row per credit at another institution reported to the bureau | `SK_ID_BUREAU` | N:1 -> application (SK_ID_CURR) | GROUP BY SK_ID_CURR after joining bureau_balance rolled up per SK_ID_BUREAU |
| `bureau_balance` | one row per bureau credit per month | `SK_ID_BUREAU, MONTHS_BALANCE` | N:1 -> bureau (SK_ID_BUREAU) | GROUP BY SK_ID_BUREAU (months, delinquent months, worst status), then rolled to SK_ID_CURR |
| `previous_application` | one row per previous Home Credit application | `SK_ID_PREV` | N:1 -> application (SK_ID_CURR) | GROUP BY SK_ID_CURR (counts, rates, means) |
| `installments_payments` | one row per (previous loan, installment number, version) payment record | `SK_ID_PREV, NUM_INSTALMENT_NUMBER, NUM_INSTALMENT_VERSION, DAYS_ENTRY_PAYMENT, AMT_PAYMENT` | N:1 -> previous_application (SK_ID_PREV) | GROUP BY SK_ID_CURR (late share, days late, payment ratios, last-12-month window) |
| `credit_card_balance` | one row per credit card (SK_ID_PREV) per month | `SK_ID_PREV, MONTHS_BALANCE` | N:1 -> previous_application (SK_ID_PREV) | GROUP BY SK_ID_CURR over card-months (utilisation, DPD) |
| `POS_CASH_balance` | one row per POS/cash loan (SK_ID_PREV) per month | `SK_ID_PREV, MONTHS_BALANCE` | N:1 -> previous_application (SK_ID_PREV) | GROUP BY SK_ID_CURR over loan-months (DPD only; deliberately small) |

Join path: `bureau_balance -N:1-> bureau -N:1-> application`; `installments / credit_card / POS_CASH -N:1-> previous_application -N:1-> application`. Each history source is aggregated to one row per `SK_ID_CURR` *before* joining, so the final left joins are 1:1 and cannot fan out the training grain (asserted by the unique test on the applicant key and by `test_integration`).

## 4. Feature families and rationale

- **A. application raw** (29): Core underwriting inputs known on the application form: income, credit, annuity, goods price, employment/age, external scores. Kept raw because these are the most predictive and auditable inputs.
- **B. affordability ratios** (8): Credit/income, annuity/income, implied term: the debt-service view an underwriter uses. Ratios are computed in one Python function shared by training and serving to prevent skew.
- **C. bureau history** (17): How much external debt, how overdue, how long a history: classic bureau-style attributes. Rolled up from credit-level and monthly-status grain.
- **D. previous applications** (12): Behaviour at this lender: refusal rate and volume are strong prior-risk signals. Only decision-time fields.
- **E. installment behaviour** (8): Realised payment discipline on earlier loans (lateness, underpayment, recent window). Restricted to payments dated on/before the application.
- **F. credit-card behaviour** (8): Utilisation and delinquency: revolving-credit stress.
- **G. POS/cash behaviour** (3): Only DPD summaries; other fields add little beyond installments and bloat the feature count.
- **H. history presence** (5): Explicit has-history flags so 'no history' (thin file) is distinguishable from 'zero events'.

## 5. Leakage audit

Three classes were audited explicitly.

1. **Target leakage** - any column that is, or is derived from, `TARGET`. Control: `TARGET` is read only in `stg_application` and only used as `y`; `build_features` takes a frame and returns exactly `FEATURE_COLUMNS`; `assert_no_forbidden` runs in `data.split_frames`; static SQL scan in `tests/test_leakage.py`.
2. **Temporal leakage** - history rows dated after the application. Control: every intermediate dbt model carries a guard (`days_credit <= 0`, `days_decision < 0`, `days_instalment <= 0`, `months_balance < 0`), tested statically and by an independent pandas re-implementation in `tests/test_integration.py` using fixtures that contain deliberate future-dated trap rows.
3. **Post-outcome information** - fields written after the loan outcome is known (realised end dates, termination). Control: never staged (table below).

### Excluded / guarded fields

| field | source | class | handling |
|---|---|---|---|
| TARGET | application_train | target leakage | The label. Only ever read as `y` in stg_application; never in any feature SQL (test_leakage). |
| SK_ID_CURR / SK_ID_PREV / SK_ID_BUREAU | all | identifier | Keys, not signal; excluded from the matrix (a row id can encode ingestion order). |
| CODE_GENDER | application_train | policy | Protected attribute; not selected in staging. `days_birth` (age) IS used - see Residual risks. |

| Installments with DAYS_INSTALMENT > 0 or DAYS_ENTRY_PAYMENT > 0 | installments_payments | temporal | Rows describing the future relative to the application are filtered in int_installments_agg. |

## 6. Residual risks (not eliminated)

- **No absolute dates.** Home Credit provides only relative days, so true point-in-time reconstruction cannot be verified; the guards rely on the dataset's own relative-day semantics. Train/valid/test is a *deterministic hash split*, not a time split, so reported performance is an in-time estimate and will be optimistic relative to a genuine out-of-time deployment.
- **Snapshot semantics of bureau amounts.** `AMT_CREDIT_SUM_DEBT` etc. are documented as of the application; we cannot verify from the data that none were refreshed later.
- **`EXT_SOURCE_*`** are third-party scores of undisclosed construction; they are available at application time but their own lineage is opaque and they dominate the model. Dependence on them is a governance risk.
- **Age (`days_birth`)** is retained as an underwriting input; use of age may be restricted by regulation in some jurisdictions. `CODE_GENDER` is excluded. No fairness audit has been performed.
- **Presence flags** (`has_*_history`) reflect data-provider coverage and could proxy for population segments.
