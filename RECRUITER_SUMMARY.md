# Recruiter summary (two-minute read)

1. **Business question.** Can historical applicant and credit-behaviour data become a reproducible risk-scoring pipeline that estimates probability of default and can be deployed and monitored safely? (It estimates PD; it does not make lending decisions.)

2. **Problem.** Default is rare, the signal sits in seven relational tables at different grains, and many columns describe the future relative to the application, so naive joins leak outcomes and fan out rows.

3. **Dataset.** The public Home Credit Default Risk files from Kaggle (applications, bureau and bureau balance, previous applications, installments, credit-card and POS/cash balances). Licence-gated, so not bundled; the pipeline locks each file's checksum and checks published row counts.

4. **Architecture.** Raw CSV → validated, immutable Postgres `raw` → dbt staging → dbt intermediate aggregates → feature and training tables → logistic baseline and LightGBM → MLflow registry (champion/challenger) → FastAPI with a Postgres audit trail → Prometheus/Grafana. Orchestrated by Prefect; tested with pytest; built in GitHub Actions.

5. **Main data-engineering challenge.** Time and grain: every history table is relative to the application date and sits at a finer grain than the applicant. Each source is filtered to records that existed at application time and aggregated to one row per applicant *before* joining, so features cannot fan out the training grain or contain post-outcome information. Proven by static SQL scans and by an independent pandas re-implementation compared to the dbt output on fixtures that contain deliberate future-dated trap rows.

6. **Important design decision.** One shared Python function builds the model inputs for both training and serving, while heavy history aggregates are precomputed in dbt and looked up online — removing training/serving skew without recomputing millions of rows per request. Also: the API fails closed if the audit write fails.

8. **Failure encountered.** A dependency upgrade silently broke MLflow's tracking store; a misconfigured tracking URI made training hang in retries before doing any work; and a first version let a fixture run write a plausible-looking plot into the results folder. Fixes: pinned versions, explicit stores per environment, and a results generator that refuses non-canonical data. Details in the README.

9. **Trade-off.** A deterministic hash split instead of a time split: the dataset has no calendar dates, so out-of-time validation is impossible. It makes results reproducible but optimistic for a real deployment — stated, not hidden. Similarly, drift detection is instrumented and tested with injected shifts, but no production drift has been observed because there is no production.

10. **What I would change at enterprise scale.** Move heavy aggregation to a warehouse or lakehouse with incremental, partitioned dbt models; a feature store with point-in-time joins and absolute event timestamps; managed secrets, TLS and network policy; a streaming or async audit sink with an outbox instead of a synchronous write; shadow/canary deployment with delayed-outcome back-testing; a model risk review including fairness and adverse-impact testing; and SLOs derived from real traffic rather than proposals.
